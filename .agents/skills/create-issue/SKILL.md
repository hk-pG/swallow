# Issue を作成する

チャットや調査結果を **GitHub Issue に残す**。正本は GitHub（`docs/github-tracking.md`）。
人の確認を待たず作成まで進めてよい。**作成したら止める**。実装・ブランチ・PR は依頼があるまでやらない。

```
進捗:
- [ ] 1. 重複確認
- [ ] 2. 種別・メタデータ決定
- [ ] 3. 本文作成
- [ ] 4. gh issue create
- [ ] 5. 報告（URL のみ。実装しない）
```

## 0. いつ使うか

| きっかけ                                 | すること                                                               |
| ---------------------------------------- | ---------------------------------------------------------------------- |
| 「Issue にして」「Issue を作って」       | このスキルで作成して **止まる**                                        |
| 不具合を直したいが Issue が無い          | このスキルで作ってから `issue-to-pr` へ                                |
| 機能・リファクタ・調査の依頼を記録したい | このスキルで作成して止まる（着手指示が別にあればその後 `issue-to-pr`） |

実装まで一気に進める依頼（「#N をやって」「Issue から PR」）は **先に Issue がある前提**で `.agents/skills/issue-to-pr/SKILL.md` を使う。Issue が無ければ、ここで作ってから渡す。

## 1. 重複確認

リポジトリルートで `gh` を使う。

```sh
gh issue list --search "<キーワード>" --state open --limit 20
gh issue list --search "<キーワード>" --state all --limit 20
```

- 同じ受け入れ条件の **オープン Issue** があれば新規作成しない。URL を返し、必要ならコメントで追記する（`gh issue comment`）
- クローズ済みで再発・続きなら、関連として本文に `#N` を書き、新規を作ってよい
- 関連ドキュメント（`docs/`、設計メモ、マージ済み PR）もざっと見て、既決と矛盾しないか確認する

## 2. 種別・メタデータ

GitHub の Issue テンプレート（`.github/ISSUE_TEMPLATE/`）に合わせる。

| 種別                                     | タイトル接頭辞 | 種別ラベル    | テンプレート        |
| ---------------------------------------- | -------------- | ------------- | ------------------- |
| 不具合                                   | `[bug] `       | `bug`         | `bug.yml`           |
| プロダクト機能                           | `[機能] `      | `enhancement` | `feature.yml`       |
| リファクタ・調査・ドキュメント・ハーネス | `[依頼] `      | `enhancement` | `agent_request.yml` |

### 必須ラベル（作成時に全部付ける）

エージェントは作成後に本文・ラベル・Milestone を編集しない（`AGENTS.md`）。**`gh issue create` の時点で揃える**。

1. **種別**: `bug` または `enhancement`
2. **領域**（どれか。複数可）:
   - `area:desktop` … Tauri / React デスクトップ
   - `area:extension` … Chrome 拡張
   - `area:ci` … CI / フック / エージェント基盤 / スキル
3. **優先度**（どれか）:
   - `P1` … α／β に必要、またはセキュリティ・データ損失に近い
   - `P2` … β 向けの通常機能・改善
   - `P3` … backlog・任意・後回し

迷ったら `P2` + 主領域。ドキュメントのみやハーネスは多くが `P3` + `area:ci`。

### Milestone

| Milestone | 目安                                               |
| --------- | -------------------------------------------------- |
| `beta`    | P1/P2 の製品機能・バグ                             |
| `backlog` | P3、後続、拡張の長期、エージェント基盤の非急務     |
| `alpha`   | 原則付けない（トラッカー用。新規作業には使わない） |

## 3. 本文

日本語。**受け入れ条件は必須**（チェックリスト）。`issue-to-pr` がこれを転記して PR にする。

チャットでの調査結果・再現・方針は本文に要約する（後から探せないメモにしない）。

### バグ

```markdown
## 何が起きているか

（期待と実際の差を短く）

## 再現手順

1.
2.
3.

## 期待する結果

## 実際の結果

## 受け入れ条件

- [ ] 上記手順で再現しなくなる
- [ ] （回帰防止のテストや追加条件）

## 原因仮説（任意）

## 関連

- （Issue / PR / ドキュメント）
```

### 機能

```markdown
## 背景

（なぜ今それが必要か。現状の UI / コードの位置）

## 現状

- （いまどうなっているか）

## やってほしいこと

1.
2.

## 受け入れ条件

- [ ]
- [ ]

## スコープ外

- （やらないこと）

## 関連

- （設計ドキュメント、先行 PR、依存 Issue）
```

### 依頼（リファクタ・調査・ドキュメント等）

```markdown
## やりたいこと

（何ができれば完了か 1〜3 文）

## 受け入れ条件

- [ ]
- [ ]

## やらないこと

-

## 補足

- （触る場所、依存、既存方針）
```

### 本文の品質チェック

- 受け入れ条件は **検証可能な文**（「〜できる」「〜が無い」「再起動後も残る」）
- 1 Issue = 1 まとまり。別機能は別 Issue
- 依存があるなら `#N` で明示する（未完了依存だけでは作成は拒否しない。着手時に `issue-to-pr` が中断する）
- 秘密情報・トークンを書かない

## 4. 作成

```sh
gh issue create \
  --title "[機能] 短い要約" \
  --label "enhancement,area:desktop,P2" \
  --milestone "beta" \
  --body-file /tmp/issue-body.md
```

- `--body-file` を推奨（シェル引用で崩さない）
- ラベルはカンマ区切りで一度に指定する
- 成功したら URL と番号を控える

作成後に直したいことがあっても、**エージェントは Issue の本文・ラベル・Milestone を edit しない**。誤りが致命的なら利用者に伝え、コメントで補足する（`gh issue comment <N> --body-file …`）。

## 5. 報告と次の一手

報告すること:

- Issue URL
- タイトル、ラベル、Milestone
- 重複で作らなかった場合はその旨と既存 URL

**ここで止める**（ユーザーが「Issue にして」とだけ言った場合の正本は `AGENTS.md`）。

続きを頼まれたら:

```sh
# .agents/skills/issue-to-pr/SKILL.md に従う
scripts/agent/start-issue.sh <N>
```

## 中断・作らない条件

- オープンな重複 Issue がある（既存を返す）
- 利用者の意図が「メモだけ」「まだ Issue にしない」と明示されている
- リポジトリ書き込み権限がなく `gh issue create` が失敗する（権限とエラーを報告）
